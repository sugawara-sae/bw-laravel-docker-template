## Todo論理削除

### 6.traitとclassの違いとは
traitはあるクラスに追加の機能（メソッド）を埋め込むための仕組みであり、それ自体ではインスタンス化できず、クラスに use して使う。
class はインスタンス化できる独立した構造で、オブジェクトとして振る舞い、継承やプロパティを持つことができる。
<!-- 
PHPでは多重継承（複数の親クラスを継承する）ができないため、
共通処理を trait にまとめて、必要なクラスにだけ use して再利用する。
 -->


### 7.traitを使用するメリットとは
PHPはクラスの多重継承ができないが、traitを使えば複数の共通処理を一つのクラスに取り込むことができる。
<!-- 
他のメリット：
・コードの重複を減らして保守性アップ
・特定の機能だけ切り出してシンプルに保てる = クラスがごちゃごちゃせず、機能ごとに整理できる

間違えやすい点：

①　×「モデルを組み合わせる」　◯「機能（処理）を組み合わせる」
traitは、モデル同士を“合体”してるわけではなく、共通の「機能」や「メソッド」を再利用してる。

② traitは「クラスを継承する代わりに使う」ものではない。
継承とtraitは別の目的の仕組み。
「継承できないからtraitを使う」わけではなく、
「同じ処理をいろんなクラスに使いたいからtraitを使う」という考え方のほうが正確。
 -->

### 13.MVCはどういったアーキテクチャか
「Model（モデル）」「View（ビュー）」「Controller（コントローラー）」の三つの役割に分けたアーキテクチャ。
<!-- 
この設計は、アプリケーションの構造を役割ごとに明確に分離することで、保守性や拡張性を高める目的がある。

Model（モデル） = データやビジネスロジックを司る部分。データベースとのやり取りなど、情報の根幹を担う存在。
View（ビュー） = ユーザーに見せる画面。見た目を整えることに責任を持ち、モデルの中身を直接いじることは許されない！
Controller（コントローラー） = ユーザーからの入力（リクエスト）を受け取り、適切なModelとViewへ処理を振り分ける調整役。
アーキテクチャ = どういう目的で、どのようなルールや役割分担をもって構築されているか、という全体的な設計の考え方。
 -->

Laravelが使用しているORMは Eloquent。
<!-- 
ORMでは、SQLを直接書かずに、クラスやメソッドでデータの操作ができるようになる。
さらにEloquentでは、モデルクラスとテーブルを1対1で紐付けて、DBとのやりとりを直感的に記述できる。
 -->


### 15.composer.json, composer.lockとは何か
Laravelプロジェクトのライブラリ管理を支える設定ファイル。
<!-- 
composer.json：プロジェクトで「必要なライブラリ」や「バージョンの条件」などを記述するファイル。必要なものリスト。
composer.lock：実際にインストールされたライブラリの正確なバージョンや構成が記録されているファイル。
                複数人で開発する場合に、全員の環境で同じバージョンのライブラリを使うために必要。

【なぜ2つとも必要なのか？】
composer.json は「何が必要か」を共有する。
composer.lock は「実際に使っているものをロックしておく」ことで、開発環境を統一できる。
この2つがあることで、開発のズレや不具合を防ぐことができる。
 -->


### 16.composerでインストールしたパッケージ（ライブラリ）はどのディレクトリに格納されるのか
vendorディレクトリ
<!-- 
【3つのファイルの関係性】
composer.json = 設計図
composer.lock = 材料発注書
vendor/ = 実際の材料  /  ダウンロードされた実際のコード  /  外部ライブラリの倉庫
          Composerで入れた便利セットが、全部入ってるフォルダ！

【覚えておきたいポイント】
・Git管理はしない（.gitignoreに入れる）
・基本的に vendor/ は触らない。手で書き換えると不整合が起きやすいため。
・composer install でいつでも復元可能
・チーム開発では composer.lock を共有
・本番環境ではサーバー側でインストール
 -->
